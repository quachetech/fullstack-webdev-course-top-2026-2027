## 🔧 What I Did

### Built the Boilerplate

Created the project folder and file via terminal, then typed out the full
boilerplate manually in VS Code:

```bash
mkdir html-boilerplate
cd html-boilerplate
touch index.html
code index.html
```

```html
<!DOCTYPE html>
<html lang="en">
    <head>
        <meta charset="UTF-8">
        <title>My First Webpage</title>
    </head>
    <body>
        <h1>
            Hello World!
        </h1>
    </body>
</html>
```

### Viewed the Page

Used **Live Server** in VS Code to view the rendered page in Google Chrome.
Live Server launches a local development server and auto-refreshes the browser
whenever changes are saved — a much cleaner workflow than manually reopening
the file each time.

### Validated the Code

Ran the HTML file through the **W3C Markup Validation Service** to check for
errors and confirm the code meets current HTML standards. Clean validation —
no errors.

### Committed and Pushed to GitHub

```bash
git add .

```

## 💡 Key Insights

**The genotype/phenotype analogy:** The `<head>` element is the genotype of
the page — configuration and metadata that shapes how the page functions,
invisible to the user. The `<body>` is the phenotype — the expressed output
the user sees and interacts with. A useful mental model for understanding why
certain things belong in `<head>` and others in `<body>`.

**On the doctype declaration and browser rendering:** Since web browsers are
programs, they must contain rendering engines capable of interpreting different
versions of HTML. The doctype declaration acts as an instruction that tells the
browser which rendering ruleset to apply. Different HTML versions have different
parsing rules — the doctype ensures the correct one is used for the document
being read. This is worth exploring further as browser internals come up in
future lessons.

**The `!` shortcut in VS Code** populates the full boilerplate automatically
in a blank `.html` file. Useful for speed once the structure is already
understood from building it manually — which is exactly the order it was
learned today.

**W3C validation as a habit:** Running code through the validator before
committing is a quality check worth building into the workflow from the start.
Catching malformed HTML early is far less painful than hunting for structural
errors in a large document later.
